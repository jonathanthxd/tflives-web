# TFLives v0.17.0 — bases de rendimiento

## Referencia y alcance

Referencia original: `main`, `34a8df7373996cc4dcaaed36bd20c816377f486a`, versión 0.16.0. Rama de implementación: `perf/v0.17-foundation`. Se conserva el diseño, los diccionarios es/en, todas las tipografías, los IDs y almacenamiento de Studio, acentos, cursores, efectos y catálogo cosmético. No se modifican migraciones, APIs, políticas de autenticación/autorización ni reglas de economía/progresión.

El entorno original ejecutable instaló Next 16.3.5, React 19.2.4 y Prisma 5.22.0. La candidata fija Next y eslint-config-next **16.3.8**, incorporando el parche crítico de [GHSA-vcvr-r3jv-pc5j](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j) y los avisos adicionales corregidos en este parche, como [SSRF en optimización de imágenes](https://github.com/advisories/GHSA-cjq9-62q9-8jv4) y [caché de Draft Mode](https://github.com/advisories/GHSA-3w37-wq28-93x7). La aplicación no configura `images.remotePatterns` ni utiliza Draft Mode; corregir la dependencia no demuestra exposición a esos casos. Se mantiene la serie 16.3, sin actualización masiva de dependencias.

Chromium automatizado puede no solicitar el favicon como un navegador interactivo; se comprueban también sus endpoints y formatos directamente.

Seis fuentes opcionales de Studio dejan de precargarse en cada ruta: Nunito, Outfit, Fredoka, Chakra Petch, Quicksand y Rubik. Se conservan declaraciones, variables, pesos, CSS de ajuste y preferencias guardadas. Inter, Space Grotesk, JetBrains Mono y Geist conservan su configuración inicial. El navegador solicita una fuente opcional cuando su CSS pasa a utilizarse, incluidas las preferencias restauradas. Las visitas con fuente guardada se miden aparte: esta estrategia puede retrasar su descarga frente a la precarga; no se oculta ese coste.

La primera candidata también retrasaba VT323 y Pixelify Sans. Las visitas frías mostraron una regresión: CLS de VT323 móvil pasó de 0,018 a 0,163 y Pixelify móvil de 0,017 a 0,138. Se restauró la precarga de ambas fuentes antes de publicar. No se conserva esa reducción adicional de bytes a costa de la estabilidad visual.

Se probó dividir el chat global mediante `next/dynamic`. En la medición con todas las peticiones iniciales completadas bajó unos 10,6 KB en páginas públicas, pero la candidata aumentó 13,7 KB de JavaScript en mensajes y 10,8 KB en configuración. Se retiró esa división antes de publicar y se volvió a medir; no se conserva una optimización con una penalización observada en rutas privadas. La funcionalidad completa se conserva. Los siete motores de fondo ya tenían importación dinámica: no se atribuye a esta versión una optimización que existía antes.

Una medición intermedia expuso un salto de login (CLS 0,625 en un estado) cuando el fallback vacío de Suspense dejaba subir el footer antes de aparecer el formulario. Se reserva la misma altura mínima de pantalla que ocupa el formulario. No cambia su diseño final ni autenticación. La validación adicional inspecciona el HTML inicial sin ejecutar JavaScript para comprobar la posición del footer, además de repetir las visitas normales con JavaScript.

## CI, higiene y pruebas

CI usa Node 24, `npm ci` con lockfile, caché npm y de `.next/cache`, permisos `contents: read` y checkout sin credencial persistida. Genera Prisma una vez; lint, TypeScript y unitarios preceden al build. El prerender usa PGlite con todas las migraciones en vez de una URL ficticia sin servidor. HTTP smoke, integración y Chromium se ejecutan secuencialmente. Publica capturas y JSON de laboratorio como artefactos de 14 días. La concurrencia cancela sólo ejecuciones obsoletas de PR, no checks de `main`.

El [último CI de la referencia original](https://github.com/jonathanthxd/tflives-web/actions/runs/35386459789) falló en el paso Lint: TypeScript, unitarios y build quedaron omitidos. Se verificaron los pasos de ese run en GitHub. Por ello no se promete una reducción de duración total frente a un pipeline anterior que no terminaba; el objetivo verificable es ejecutar todos los controles y eliminar la generación duplicada.

Se ignoran nuevos artefactos de navegador, logs, `.bak` y `.tmp`. ESLint excluye sólo esos resultados generados, manteniendo el análisis de código y pruebas. Ya se ignoraban ZIPs. Se conserva `backups/tflives-web-neon-better-auth.zip`: 361 entradas, ningún `.env`/`.env.local`/`.env.production` y un ejemplo de entorno, comprobado por nombres sin publicar contenido. También se conserva el ejemplo alternativo ya versionado; no se presupone que un archivo histórico sea prescindible. No se añade ningún secreto, backup o estado de sesión a los cambios.

Lint original: **39 errores y 17 advertencias**. Se reparan efectos con actualizaciones síncronas redundantes, lecturas de refs en render y el componente Metric declarado dentro de render. Las respuestas asíncronas actualizan estado desde las promesas de red reales; se conserva su manejo de permisos/errores. Las preferencias y valores iniciales del navegador usan snapshots explícitos con fallback de hidratación, y los object URLs tienen ciclo de creación/revocación después del montaje. No se deshabilitan reglas para aprobar el chequeo. Permanecen 17 advertencias previas (principalmente imágenes y navegación interna); no son nuevas optimizaciones ni errores ocultados.

El primer `npm test` sin entorno falló al importar una URL de base no definida. El bootstrap de unitarios ahora impone una URL local sin servidor: la suite usa sus PGlite internos y no requiere `.env`. Los **112 tests** (109 existentes y tres guardas de formatos/tamaños de iconos) pasaron. TypeScript pasó y Prisma genera correctamente su cliente 5.22.0.

La auditoría tras fijar 16.3.8 informa **0 críticas, 11 altas y 5 moderadas**, sin avisos para el paquete Next. La referencia tenía 1 crítica, 11 altas y 5 moderadas. Los restantes avisos implican, entre otros, la cadena de herramientas CSS/ESLint; las propuestas automáticas incluyen cambios mayores e incluso versiones anteriores de eslint-config-next. No se aplica `audit fix --force` ni se declara el árbol completamente libre de vulnerabilidades. Su resolución requiere revisar exposición y compatibilidad por dependencia.

## Método y limitaciones

Las comparaciones principales usan `next build` con Turbopack y `next start`, Node 24.20.0 y el mismo Chromium. Para aislar las optimizaciones, el código original se recompila con el mismo parche de Next 16.3.8 que la candidata. Su checkout de prueba usa `turbopack.root` en el padre común únicamente para permitir un node_modules enlazado; la configuración de producción no cambia. Los hashes/build IDs constan en los JSON. Las ejecuciones anteriores en 16.3.6 son diagnósticas y se repiten tras actualizar el parche.

En Windows, el transporte HTTPS que usa la descarga de fuentes de Next no completó las solicitudes, aunque `fetch` sí podía descargarlas. Se usa la caché explícita de **57 WOFF2 reales**, con CSS, firmas y SHA-256; ambos builds reciben exactamente los mismos bytes. Ver [protocolo reproducible](./PROTOCOL.md). Los intentos con webpack y una caché de URLs de archivo no constituyen la comparación principal: el primero no reprodujo las precargas de fuentes; el segundo era incompatible con Turbopack. Los fallos se investigaron antes de elegir el mecanismo que compila el bundler habitual.

Next también emite en el código original la advertencia E1163 de calentamiento de caché. Se conserva el log completo y el recuento en `server-diagnostics.json`; el harness distingue esa `console.warn` conocida de excepciones reales y fallos Prisma, que hacen fallar la prueba. Un ajuste exploratorio de Cached Navigations no la eliminó y se revirtió. No se atribuye su causa con certeza al [problema upstream #98543](https://github.com/vercel/next.js/issues/98543), que documenta un síntoma relacionado; se recomienda una reproducción aislada y validar el siguiente parche estable. No se desactivan Cache Components ni partial prefetch.

No hay acceso a RUM, INP real, teléfonos físicos o tráfico de producción. FCP/LCP/CLS y tareas largas son observaciones locales con viewport móvil y GPU software. La suma de bloqueo **no es INP ni TBT de Lighthouse**. Una observación por estado no prueba una mejora estadística de latencia. OAuth externo, envío de email/Discord y subida a almacenamiento externo requieren credenciales/servicios que no se ejercitan aquí.

## v0.18 por impacto

1. **Precarga condicionada por la preferencia guardada y fuentes por ruta**, manteniendo las nueve opciones y midiendo CLS/latencia de fuente en visitas frías. Una cookie/contrato nuevo necesita diseñarse aparte.
2. **Presupuesto de JS y previsualizaciones de Studio**: perfilar montaje, liberación WebGL, compilación de shaders y chunks en hardware real. Preservar efectos y animaciones; separar por uso sin reducir la identidad.
3. **CSS por módulo** con inventario de clases, cobertura y pruebas de todos los cosméticos. Evitar borrar estilos por una medición parcial de cobertura.
4. **Caché de Network/Next**: aislar E1163, comparar versiones estables y verificar navegación caliente con contenido poblado. No confundir caché del build con datos representativos de producción.
5. **RUM e INP reales** con consentimiento, privacidad y presupuesto acordados; contrastar móvil físico/red lenta con el laboratorio.
6. **Imágenes de contenido, dependencias y archivos históricos**: resolver las advertencias restantes con fidelidad visual; evaluar vulnerabilidades transitivas y retirar backups sólo tras confirmar su función.
