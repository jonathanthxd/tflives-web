# TFLives v0.18.0 — Frontend Performance

## Resumen y referencia

La referencia es v0.17 ya integrada en `main`, commit `c79fd260b297bba86ce493f0cc7b81d811743fa0`. Su CI pasó en [37719000912](https://github.com/jonathanthxd/tflives-web/actions/runs/37719000912) y su estado Vercel era satisfactorio al comenzar esta misión. Se recompiló esa referencia y se recogió una nueva matriz; las cifras de v0.16 del [informe anterior](V0_17.md) no son la base de esta comparación. Rama: `perf/v0.18-frontend`; [PR #2](https://github.com/jonathanthxd/tflives-web/pull/2).

La reducción principal procede de separar el motor Three/R3F/Drei del equipo de la aplicación compartida. También se reduce el CSS recibido mediante una frontera cliente que permite cargar los estilos de la constelación donde se necesitan. Las animaciones activas conservan sus parámetros y calidad; se evita trabajo gráfico, peticiones y respuestas obsoletas cuando ya no son útiles. Studio, el selector de emojis y el editor de imágenes conservan su apertura inmediata después de rechazar sus divisiones pequeñas por latencia.

No se cambian Next 16.3.8, React 19.2.4, Prisma 5.22.0 ni las dependencias bloqueadas. `package.json` y la raíz del lockfile pasan a 0.18.0. No hay cambios en APIs, infraestructura de autenticación, esquema, migraciones, permisos, economía o reglas de progresión. Los datos de prueba viven exclusivamente en PGlite local. Se conservan los informes y evidencias históricas de v0.17.

## Problemas observados y cambios retenidos

### Recursos iniciales y constelación

La función de posiciones del equipo compartía módulo con su renderer: importar una función pequeña alcanzaba Three, Fiber y Drei. En la referencia, un recurso inicial de 660.038 B sin comprimir / 166.101 B recibido incluía Three; otro de 158.697 / 50.376 B formaba parte de la cadena gráfica. Estas cifras describen chunks observados, no se suman a la reducción global como ahorros independientes.

`team-space.ts` contiene el cálculo determinista original sin cambios. La frontera cliente `team-constellation-loader.tsx` permite dividir el componente desde su sección servidor. El campo 3D tiene su propia importación dinámica y se monta al acercarse a 480 px del viewport. Las tarjetas, nombres, cosméticos y controles conservan su HTML inicial; no se sustituye la escena por una ilustración estática. Tras cargarla se mantiene montada: fuera de pantalla o con el documento oculto usa renderizado bajo demanda; al regresar vuelve al bucle continuo. Los observadores y el listener de visibilidad se desconectan al desmontar.

Se mantienen cámara `[0,0,7.8]`, fov 48, DPR `[1,1.65]`, antialias, 950 estrellas, speed 0.2 y todas las posiciones, geometrías y movimientos originales. La navegación entre miembros usa el mismo desplazamiento y transición de 0,34 s. La prueba separada con equipo poblado mide el coste del renderer diferido y comprueba dibujo WebGL, uniformes temporales cambiantes, navegación, CSS, pausa y reanudación en 1440, 820 y 390 px, claro/oscuro.

La matriz principal utiliza la misma base pequeña y equipo vacío en ambas versiones. La prueba poblada requiere fixture **durante la compilación**, porque la sección se prerenderiza. No se compara el peso de una página poblada con el de una página vacía para inventar un ahorro. El resultado poblado se presenta aparte y no se extrapola a todos los tamaños de equipo o dispositivos.

### CSS y fuentes

Se trasladan 801 líneas de reglas de constelación a `team-constellation.css`, conservando selectores, declaraciones y orden relativo salvo la corrección de overflow descrita abajo. El bloque de previsualización de cursor de 53 líneas pasa a su componente. Este último sigue siendo inmediato junto con Studio; no se le atribuye una carga diferida que finalmente se rechazó. La reconstrucción de los tres archivos se compara mediante AST con `globals.css` original y admite exclusivamente esa corrección: [auditoría CSS](v0.18/data/css-audit.json). El CSS transferido se mide en el navegador, por separado del tamaño de los archivos fuente.

La revisión visual del fixture poblado encontró una tarjeta y navegación cortadas en móvil. El foco en los controles desplazaba internamente el contenedor `overflow:hidden` del mundo 3D sobredimensionado: se observaron `scrollLeft=133` y `scrollTop=101`. Cambiar sólo ese límite a `overflow:clip` mantiene su apariencia recortada e impide que funcione como área de scroll. La repetición de seis casos comprueba offsets cero y los límites de tarjeta y navegación, además de guardar capturas corregidas. No cambia el diseño ni reduce la escena.

La primera separación CSS sin la frontera cliente produjo **493 B adicionales** en la visita a inicio: no constituía una mejora. La frontera final se valida por las solicitudes reales y por la apariencia con equipo poblado. Se mantiene el algoritmo habitual de chunking de Turbopack; no se desactivan estilos, minificación, Cache Components ni partial prefetch para forzar cifras.

No se modifica la configuración de `next/font`, sus pesos, variables ni correcciones métricas. Siguen las nueve elecciones de Studio y las precargas de VT323 y Pixelify Sans restauradas en v0.17. Las seis precargas iniciales y las visitas con cada fuente guardada se comprueban de nuevo; las fuentes no forman parte del ahorro de v0.18.

### Mensajes y perfil

La pantalla de mensajes reutiliza peticiones idénticas en curso. Al cambiar de conversación o desmontar aborta las anteriores; las respuestas obsoletas no reemplazan la conversación activa. La unión incremental deduplica mensajes en una pasada, conservando la primera aparición y su orden. La búsqueda cancela tanto su debounce como la solicitud anterior. Se cancela también el frame pendiente que enfoca una respuesta. No se cambian endpoints, validadores, paginación ni permisos.

Una prueba real de envío encontró que el botón flotante de chat global tapaba «Enviar» en escritorio y móvil. En la ruta de mensajes se eleva 4 rem el lanzador y su panel, ajustando la altura disponible y conservando la safe area, arrastre y preferencias. Esta es una corrección visual intencional de una colisión, no un rediseño. Las demás rutas mantienen su posición anterior.

El perfil conserva su identidad y progreso inicial renderizados desde el servidor. Su actualización periódica no realiza peticiones si la tarjeta queda fuera de pantalla o el documento está oculto, cancela la solicitud al salir y evita solapamientos. Al volver a la vista vuelve a actualizarse. No se difieren avatar, nombre, banner, privacidad o permisos. La prueba mantiene la tarjeta fuera de pantalla durante 11 s, comprueba ausencia de polling y verifica una respuesta real al regresar.

### Motores gráficos y QR

CRT Warp antes solicitaba frames continuamente aunque el tiempo estuviera pausado, y mantenía su bucle fuera de pantalla. Ahora detiene el scheduler cuando ya no debe dibujar. En previsualización pausada deja terminar la misma inercia de puntero y después se detiene; tamaño y cambios de parámetros pueden pintar un frame real. Se conservan shaders, velocidades, smoothing y FPS originales. Al desmontar libera geometría, material, renderer, contexto, RAF, listeners y observadores.

Prism libera geometría y programa y pierde explícitamente el contexto al desmontar. Se corrige `timeScale || 1`, que convertía cero en uno y hacía avanzar una previsualización supuestamente pausada; el valor activo 0,5 y los shaders permanecen iguales. La prueba observa primero animación real, luego reposo y finalmente retirada del canvas. Los hashes de los shaders, parámetros, preferencias y código preservado constan en la [auditoría de fuente](v0.18/data/source-audit.json). Los otros cinco motores ya tenían límites de actividad y limpieza: no se atribuyen a esta versión mejoras preexistentes.

El encoder QR se importa sólo después de una respuesta auténtica y válida de activación 2FA. El formulario, autenticación y errores siguen siendo los mismos. La primera activación se mide con cuenta y contraseña efímeras locales; se valida un PNG de 192 px sin guardar URI TOTP ni códigos de recuperación. El coste de esa importación se registra como recurso diferido, no desaparece del producto.

## Cambios rechazados

Se ensayó diferir Studio, el selector de emojis y el editor de imagen. Ocho observaciones por herramienta mostraron que la primera apertura empeoraba: Studio pasó de una mediana de 305,35 a aproximadamente 600,05 ms; editor de 143,9 a aproximadamente 416 ms; selector de 372,1 a aproximadamente 516,6 ms. Las divisiones sólo evitaban unos 4 KB, 3 KB y 4,6 KB respectivamente y añadían coste de importación/montaje; el prefetch por intención no compensó la penalización observada. Se restauraron sus componentes originales y se repitieron las interacciones y la matriz completa.

Estos tiempos son observaciones locales de automatización, no INP ni prueba estadística. Se conservan las muestras del ensayo para explicar el rechazo. No se repite la división de GlobalChat descartada en v0.17, ni se propone una carga diferida genérica como solución. Tampoco se eliminan fuentes, presets, efectos premium o movimientos, ni se reduce DPR, número de estrellas o velocidad para lograr un resultado favorable.

### Escenario adicional: equipo poblado

En los seis casos corregidos se reciben inicialmente 288,0 KB de JS, 47,5 KB de CSS y no se crea el canvas fuera del umbral. El CSS del equipo sí está disponible desde el primer renderizado para conservar identidad y controles. **La reducción CSS de la matriz vacía no se extrapola a esta página poblada**; la frontera añade un stylesheet y su overhead. No existe una matriz poblada original equivalente que permita publicar un porcentaje específico para este escenario.

Al saltar directamente desde arriba a la escena fría, se descargan 222,0 KB adicionales de JS y 0 B de CSS. Dibujo y uniformes temporales reales se observan entre 1139 y 1716 ms; mediana 1248 ms. El JS total tras utilizarla es 510,0 KB: los bytes del motor se posponen, no desaparecen. Las tarjetas y controles son independientes de su arranque; el margen de 480 px prepara la escena al acercarse. Un salto frío brusco conserva este coste medido y no se promete renderizado instantáneo. Se conserva la frontera por evitar una descarga gráfica grande y trabajo fuera de vista en el arranque, y se deja su verificación física/RUM como límite.

Los seis casos comprueban tarjeta/navegador dentro del arena, offsets internos cero, navegación entre miembros, pausa efectiva y reanudación. [Datos completos del equipo](v0.18/data/team/visual-checks.json).

## Reproducción

Usar el lockfile y Node 24; generar Prisma, ejecutar lint, tipos y unitarios. La compilación de laboratorio usa las migraciones versionadas en una base local efímera, nunca Neon de producción. En este Windows el transporte de fuentes de Next requiere la caché explícita de 57 WOFF2 reales; referencia y candidata comparten esos bytes. En CI se usa `build-isolated.mjs` con la descarga habitual. Ver [protocolo](PROTOCOL.md).

```powershell
npm ci
npm run db:generate
npm run typecheck
npm run lint
npm test
npm run perf:cache-fonts
npm run build:lab:cached
npm run test:e2e
npm run test:integration
$env:TFL_PERF_OUTPUT='performance-artifacts/v18/final'
$env:TFL_GRAPHICS_CHECKS='1'
npm run test:visual
```

La comparación primaria ejecuta ambos builds con `TFL_INTERACTIONS` sin activar para conservar la misma secuencia de navegación. Ejecutar las aperturas en otro destino con `TFL_INTERACTIONS=1`, `TFL_QR_CHECK=1`, `TFL_VISUAL_EXTENDED=0` y `TFL_ROUTE_FILTER='/,/configuracion,/mensajes,/perfil/visual_fixture'`: 32 estados, ocho observaciones de cada herramienta y dos activaciones QR. Registrar bytes después de completar los recursos diferidos, además del instante en que la herramienta ya está usable; la espera de asentamiento no se presenta como latencia de apertura.

```powershell
$env:TFL_TEAM_CACHED='1'
$env:TFL_TEAM_OUTPUT='performance-artifacts/v18/team-final'
node scripts/performance/check-team-isolated.mjs
```

El comando de equipo recompila con dos miembros locales y vuelve a crear la misma base para la prueba; no basta insertar miembros después del prerender. Genera seis capturas y resultados independientes. Después recompilar normalmente si se desea volver a ejecutar la matriz vacía. No ejecutar builds, suites pesadas ni otro navegador simultáneamente con la medición. `run.json`, build IDs y el digest de fuente identifican las ejecuciones; los intentos intermedios no se usan como resultado final.
