# TFLives Web v0.4.0 rollout

## Migration

This release adds Better Auth's persistent `RateLimit` and official `TwoFactor`
tables, `User.twoFactorEnabled`, the private `SecurityEvent` log, and the
`SECURITY_ALERT` notification value.

Do not use `prisma db push` or `prisma migrate reset`. After review, run these
commands against the intended environment in this order:

```bash
npx prisma migrate status
npx prisma migrate deploy
```

The generated migration is
`prisma/migrations/20260911000000_accounts_security_permissions/migration.sql`.
It is additive and has not been applied by this repository change.

## Required environment configuration

Set the following names in the deployment environment as appropriate:

- `DATABASE_URL`
- `BETTER_AUTH_SECRET`
- `BETTER_AUTH_URL`
- `AUTH_REQUIRE_EMAIL_VERIFICATION`
- `RESEND_API_KEY`
- `AUTH_EMAIL_FROM`
- `GOOGLE_CLIENT_ID`
- `GOOGLE_CLIENT_SECRET`
- `DISCORD_CLIENT_ID`
- `DISCORD_CLIENT_SECRET`

Use `https://www.tflives.com` as the canonical production value for
`BETTER_AUTH_URL`. Preview environments must use their own explicit deployment
URL; no wildcard trusted origin is configured.

## OAuth console configuration

Register these exact callback URLs in both the Google and Discord consoles:

- Production Google: `https://www.tflives.com/api/auth/callback/google`
- Production Discord: `https://www.tflives.com/api/auth/callback/discord`
- Local Google: `http://localhost:3000/api/auth/callback/google`
- Local Discord: `http://localhost:3000/api/auth/callback/discord`

OAuth sign-in creates a new account only when no TFLives identity already owns
the provider. Matching emails are not implicitly merged. A person with an
existing account must sign in with that account and explicitly link Google or
Discord from **Configuración → Seguridad de la cuenta**. Providers must present
the same verified email; linking different-email identities is disabled.

## Operational notes

- Better Auth uses PostgreSQL-backed rate limits for auth routes, so the limits
  are shared across Vercel instances.
- Security events store a keyed IP digest and a compact device label, never raw
  credentials, OAuth secrets/tokens, reset tokens, session tokens, or recovery
  codes.
- TOTP and recovery codes are implemented through Better Auth's bundled
  two-factor plugin. The secret and recovery-code representation are managed by
  the plugin; the UI shows generated recovery codes only in the active browser
  setup/regeneration step.
- `OWNER` was intentionally not introduced: the existing data model has only
  `USER`, `MOD`, and `ADMIN`, and no existing operation needs a new role.
